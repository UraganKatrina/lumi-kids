# Архитектура LUMI Kids

Документ описывает целевую архитектуру и то, в каком порядке она появляется.
Принцип: строим только то, что нужно текущему этапу, но так, чтобы следующие
этапы не требовали переписывания.

## 1. Общая схема

```
┌──────────────────────┐      HTTPS / REST (v1)      ┌──────────────────────┐
│  Мобильное приложение│ ──────────────────────────▶ │  API (NestJS)        │
│  Flutter, Android/iOS│ ◀────────────────────────── │  модульный монолит   │
│  офлайн-первым       │    пакеты контента, прогресс│                      │
└─────────┬────────────┘                             └───┬──────────┬───────┘
          │ SQLite на устройстве                         │          │
          ▼                                              ▼          ▼
   локальный прогресс,                            PostgreSQL   Объектное хранилище
   скачанные пакеты                                            (картинки, аудио) + CDN
                                                      ▲
                                ┌─────────────────────┘
                                │
                     ┌──────────┴───────────┐
                     │  Админка / CMS       │
                     │  Next.js             │
                     └──────────────────────┘
```

Ключевые решения:

- **Офлайн-первым.** Приложение работает без сети на скачанном контенте.
  Прогресс пишется локально и синхронизируется, когда сеть появляется.
- **Задания — это данные.** Экран задания один на каждый тип упражнения,
  а конкретные задания приходят JSON-пакетами (см. [data-model.md](data-model.md)).
- **Сервер — модульный монолит.** Один процесс NestJS с чёткими модулями.
  Микросервисы не нужны, пока нет доказанной причины.
- **Минимум данных о ребёнке.** Имя (или прозвище), месяц и год рождения,
  язык, интересы. Без фото, голоса, геолокации и рекламных идентификаторов.

## 2. Структура репозитория (цель)

Один репозиторий для всех частей, чтобы контракты API и схема контента
менялись атомарно.

```
lumi-kids/
├── apps/
│   ├── mobile/          Flutter-приложение
│   └── admin/           Next.js CMS (этап 6)
├── services/
│   └── api/             NestJS API (этап 6)
├── content/
│   ├── schema/          JSON Schema заданий: единый источник правды
│   └── examples/        эталонные задания, на которых проверяется схема
├── docs/                архитектура, модели данных, план тестов, решения
└── .github/workflows/   CI для каждой части
```

## 3. Модули мобильного приложения

Код раскладывается по функциям (`lib/features/<функция>/`), внутри функции —
по слоям. Общие вещи лежат в `lib/core/`.

```
lib/
├── app/                 точка входа, тема, навигация
├── core/
│   ├── design_system/   цвета, типографика, отступы, кнопки, карточки
│   ├── l10n/            локализация ru / uz / en
│   ├── storage/         SQLite (drift), миграции
│   ├── network/         HTTP-клиент, повторы, офлайн-очередь
│   └── errors/          типы ошибок, журналирование без персональных данных
└── features/
    ├── world_map/       главная карта и острова
    ├── catalog/         12 направлений развития
    ├── exercise_engine/ движок упражнений: загрузка, отображение, проверка
    ├── content_library/ пакеты контента, версии, офлайн-загрузка
    ├── progress/        прогресс по навыкам
    ├── recommendations/ следующее занятие
    ├── rewards/         коллекция наград
    ├── profiles/        профили детей
    ├── parent_area/     родительский кабинет за родительским барьером
    ├── purchases/       подписки (этап 8)
    └── settings/        язык, звук, офлайн
```

Внутри каждой функции:

```
features/<функция>/
├── domain/        модели и правила, без Flutter и без хранилища
├── data/          репозитории: SQLite, API, файлы
└── presentation/  экраны, виджеты, состояние
```

### Правила зависимостей

- `presentation` → `domain` ← `data`. Домен ни от чего не зависит,
  поэтому он легко тестируется.
- Функции не импортируют внутренности друг друга, только публичный
  `domain` другой функции.
- `core` не зависит от `features`.

### Выбранные библиотеки (по умолчанию)

| Задача | Выбор | Почему |
|---|---|---|
| Состояние | `flutter_riverpod` | тестируемость, нет глобальных синглтонов |
| Навигация | `go_router` | официальный пакет команды Flutter, глубокие ссылки |
| Локальная БД | `drift` (SQLite) | типизированные запросы и миграции |
| JSON-модели | `json_serializable` | генерация кода вместо ручного разбора |
| Локализация | `flutter_localizations` + ARB | стандартный путь Flutter |
| Анимации персонажей | Rive — по необходимости | подключаем, когда появится персонаж |
| Мини-игры | Flame — только для отдельных игр | обычные упражнения делаем на Flutter |

Каждая новая зависимость проходит проверку: лицензия, активность поддержки,
что она собирает и куда отправляет данные.

## 4. Движок упражнений

```
Пакет контента (JSON) ─▶ проверка схемы ─▶ Task ─▶ ExerciseRenderer[тип]
                                                     │
                                       ответ ребёнка ▼
                                        Evaluator[тип] ─▶ Attempt ─▶ прогресс,
                                                                     награды,
                                                                     рекомендации
```

- Для каждого типа упражнения есть пара «отрисовщик + проверяющий».
  Новый тип добавляется регистрацией этой пары, без правки остального кода.
- Задание с неизвестным типом или с `minAppVersion` выше текущей версии
  приложения не показывается и не ломает каталог.
- Проверка ответа идёт локально, без сети.

## 5. Совместимость и версии

| Что | Как версионируется |
|---|---|
| Схема контента | `schemaVersion` (целое). Приложение знает диапазон поддерживаемых версий |
| Отдельное задание | `version` (целое), растёт при каждой правке |
| Пакет контента | `packVersion` + список заданий и хэши медиа |
| API | префикс `/v1/`, ломающие изменения только в `/v2/` |
| База на устройстве | миграции drift, номер схемы в базе |
| База на сервере | миграции, запускаются в CI на пустой базе |

## 6. Среды

| Среда | Назначение | Данные |
|---|---|---|
| `dev` | разработка, локально и в облаке | тестовые |
| `staging` | проверка перед релизом, тестовые сборки | тестовые |
| `prod` | магазины | реальные |

Секреты хранятся только на сервере и в секретах GitHub Actions,
в приложении их нет.

## 7. Безопасность детей (архитектурные правила)

- Покупки, внешние ссылки и настройки — только за родительским барьером.
- Нет чатов, нет контактов с незнакомцами, нет сторонней рекламы.
- Аналитика без персональных данных ребёнка и без рекламных идентификаторов.
- Ошибки журналируются без имён, без текста ввода и без идентификаторов устройства.
- Удаление аккаунта удаляет все связанные детские профили и прогресс.
- ИИ не публикует контент: каждое задание проходит статус `approved` у человека.

## 9. Открытые вопросы

- Юридическая проверка названия LUMI Kids.
- Возможность регистрации разработчика и получения выплат из Узбекистана
  в Google Play и App Store — проверить перед этапом 8.
- Mac для сборки iOS: свой компьютер или облачная сборка (например, macOS-раннеры GitHub Actions).
